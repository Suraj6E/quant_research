An expert review of fxpit

The apparatus is excellent, the epistemics are exceptional, and the empirical payload is thin — reviewed from a quantitative-research and an ML vantage point

{{ m.prov_badge('recorded') }}   Written 2026-08-06 against the repository at that date · This page is a snapshot and does not update with the code · Plain text: review.md

Verdict, up front

Yes, this project has merit — real merit, of a specific and somewhat unusual kind.

It is not a product, it is not a strategy, and its flagship experiment is only one-third complete by its own accounting. What it is is one of the most disciplined demonstrations of research-data hygiene this reviewer has seen at portfolio scale, with two or three outputs that are genuinely useful to people other than its author.

The project's honesty about its own thinness is itself its strongest feature — and also the thing that most needs to stop being a feature and start being fixed, because "we honestly report that we didn't get the data" is admirable exactly once.

1 What it is

A three-tier database — Postgres for reference and vintage data, ClickHouse for ticks, DuckDB as the sole query layer — whose single organizing idea is that every read goes through one implementation of known_at <= t. On top of it: a tick ingest pipeline with a crash-safe ledger, an additive quality-flag layer, a bitemporal macro store holding 586k real RTDSM vintage observations, a timezone-correct session calendar, an ECB drift anchor with demonstrated (and honestly bounded) detection power, and a pre-registered four-arm experiment decomposing backtest inflation into revision leakage, timestamp coarsening, and the mid-price assumption.

The actual empirical results, stated plainly

  • One measured number: the mid-price assumption costs +0.357 bps per round trip on EURUSD at a 30-minute hold (t = 7.56, corroborated by the independently measured 0.271 bps median spread). A real measurement; the pairing logic that makes it resolvable at n = 8 is correct.
  • One unplanned insight: revision leakage arrives through rare signal flips (paired-difference SD 26 bps vs 0.13 bps for the spread channel), so resolving a 2 bps revision effect needs ~682 events — roughly 28 years of payrolls + CPI. The project's most transferable finding.
  • Everything else: unresolved, and said so. H1 and H2 not assessed; H4 blocked.

It also produced source findings of independent value: the keyless ALFRED endpoint silently ignoring vintage_date, Dukascopy's ask-before-bid wire order, zero-based month indices, HTTP-200-empty-body weekends, and the RTDSM Sitecore hash-rotation gotcha.

2 What it should have been (vs what it is)

Judged against its own planning.md, the honest gap list:

In the stronger sense — what the ideal version of this exact idea looks like — it is the same apparatus pointed at 240+ events (2015–2024) and several instruments spanning a spread range. EURUSD's 0.27 bps median spread is the least interesting instrument on which to measure the mid-price channel; "the spread channel is small" is a statement about EURUSD, not about the channel. None of that requires new ideas. It requires patience with a rate limiter.

3 What it is pretending to be — and what it honestly is not

This project is unusually free of pretense: the pre-registration is hash-stamped, the underpowered flag is a structural property of the result object, the −1h drift-anchor miss is reported rather than hidden, and success criterion #3 is recorded as partially met rather than redefined. That said, a reviewer paid to be unkind would flag four things:

  1. The scale costume. The architecture is dressed for 2–5 billion rows; the resident data is under a million ticks. Three databases, a Postgres→ClickHouse mirror-export with a documented staleness footgun, and a materialized-view replay dance are complexity purchased against a projection the free-source constraint may prevent from ever materializing — a full 7-pair × 10-year ingest is ~600k hourly requests against a source that blocks after ~360 in a burst. planning.md is candid that ClickHouse was chosen partly as a "CV signal", which is honest — but honesty about a costume does not make it not a costume. A single DuckDB over Parquet would serve the realized scale with a third of the operational surface.
  2. "116+ tests, green" flatters the validation depth. The suite is genuinely good — the five-way mutation check is a practice most production shops skip — but the majority of tests run against hand-built fixtures. Only the 21 integration tests touch real stores, and nothing tests the system at even 1% of projected volume.
  3. The prose outruns the payload. docs/findings.md is beautifully written, and every individual sentence in it is defensible. But the cumulative effect of that polish is a document that reads like a completed study while describing a pilot with n = 8. The narrative craftsmanship is doing load-bearing work that data should be doing. A skeptical reader notices.
  4. No human has reviewed the code. The git log says so explicitly. The project's own thesis is that plausible-looking wrong output is the default failure mode of unchecked systems — and that thesis applies to code generators too. The mutation checks mitigate this substantially, but "the tests are green" and "a qualified human has read the diff" are different claims, and only one is currently true.

What it is not pretending to be, to its credit: profitable, complete, novel science, or a product. All four disclaimers appear in the README above the fold.

4 Does it have real-world use? Where?

Not directly, as software. No fund would deploy a free-data, single-node, 7-pair store, and none needs to. Indirectly, in five real places:

  1. Backtest audit and model validation. The four-regime decomposition is a ready-made audit protocol. Model-validation teams at banks and allocators doing manager due diligence ask exactly these questions informally; this turns them into a runnable harness. The most useful artifact is not the code — it is the checklist implied by the variant table.
  2. ML feature stores. The known_at <= t join is byte-for-byte the point-in-time-correct training join that Feast, Tecton, and every in-house feature store solves or fails to solve. The failure modes catalogued here are the exact mechanisms of train/serve skew and target leakage in production ML.
  3. Real-time macro research. The ALFRED keyless-endpoint finding — accepts vintage_date, silently serves current revised data, byte-identical across four requested vintages — is a genuinely useful public-interest result. Anyone who built a "real-time" study on the keyless CSV has contaminated data and no error message saying so. The single most citable thing in the repository.
  4. Teaching. As a pedagogical artifact for how research data actually goes wrong — the base-year rebasing trap, the UTC+5:45 silent timezone bug, the materialized-view-doesn't-backfill gotcha — this beats any textbook treatment, because every trap was actually stepped in and the footprints are preserved.
  5. The power-calculation framing. "How much data does anyone need before they can honestly claim to have measured revision leakage?" (answer: more than most published event studies have) is a legitimate methodological point in the Croushore–Stark real-time-data tradition, currently buried in §5 of a findings doc nobody will find.

5 Technical review — the quant's reading

Correct, and better than industry-typical

  • One implementation of the filter. known_at <= t exists in exactly one place, and a documented rule forbids a second. Most real systems fail precisely here — three teams, three "as of" implementations, one of them wrong.
  • Conservative timestamp placement. Coarse known_at placed at the latest consistent instant, so the system withholds rather than leaks. The right asymmetry, and almost nobody gets it right — the common industry choice (midnight of the vintage date) leaks up to 24 hours.
  • NULL as a fact. A release published as missing keeps its known_at and ranks normally. Correct and rare.
  • The paired-difference estimand. Comparing four Sharpes at n = 8 would be numerology; pairing on shared events and reporting per-channel deltas with SEs is the statistically right design, and the explanation of why only the mid-price channel resolves is textbook-quality.
  • The drift anchor's calibration. Demonstrating detection of +1h and +5h45m, reporting the −1h miss, and deliberately not asserting it in tests is a level of calibration discipline rarely seen in professional code.

Where the expert eyebrow goes up

  • The t-statistics assume the wrong distribution for the revision channel. Its own mechanism — rare sign flips, huge conditional impact — makes the paired differences a mixture: mostly ≈0, occasionally ±2× the event move. A t-test on that mixture is fragile at any realistic n. The fix is also the more interesting design: decompose revision leakage into P(flip) × E[impact | flip]. Flip probability needs no tick data at all — RTDSM vintages go back to 1964, giving ~700 payrolls observations today. Conditional impact is an ordinary event-study quantity. This two-part estimator shortcuts most of the 28-year data requirement the findings doc treats as a wall — the clearest place an expert collaborator would have improved the result.
  • The synthetic surprise limits external validity of the revision channel specifically. "A shared flaw is a constant across arms" is airtight for the spread and timestamp channels, but not for revision leakage, whose magnitude is precisely "how often does the surprise sign differ between first-print and revised series" — a function of the surprise construction. The measured revision channel is conditional on the synthetic measure in a way the documents do not fully acknowledge.
  • Sample selection in the 8 events. The ingest was cut off mid-run, so the priced events are the chronologically earliest — a non-random subsample. Immaterial at n = 8, but the completed run should confirm the event set was not availability-biased.
  • EURUSD-only conditionality. "The mid-price channel is small" is true of the tightest-spread instrument in the world at a 30-minute hold. The same harness on a wide-spread pair or a 2-minute hold tells a very different story — and the cross-instrument gradient is the finding a practitioner actually wants.
  • Sharpe annualized by √24 events is a stated convention, but produces numbers (2.2 at n = 8) that look like trading claims despite the underpowered banner. Reporting mean bps with CIs and dropping Sharpe entirely below the interpretability threshold would be cleaner than printing a Sharpe and disclaiming it.

6 Technical review — the ML expert's reading

There is no machine learning in this project, and that is a defensible choice — the scope guardrails explicitly forbid strategy sophistication. But the project is best understood as the data infrastructure that makes financial ML honest, and its relevance to ML is larger than its author seems to claim.

  • The as_of(t) contract is isomorphic to the point-in-time-correct training join. The date-only-query-must-raise test is the same bug class as training on date-stamped features while serving on millisecond-stamped ones — the most common silent leak in production financial ML.
  • The four arms map onto ML leakage taxonomy one-to-one: revision leakage = label/feature versioning leakage; timestamp coarsening = temporal granularity leakage; mid-price = evaluation-cost misspecification. In ML terms this is an ablation study of leakage sources on a fixed model — a design leakage papers mostly lack, because they rarely control the arms to differ in exactly one dimension.
  • The obvious ML extension that would multiply the audience: train an identical, deliberately dull model under each regime and report the validation-metric inflation per regime. That converts "backtest contamination" into "leaderboard contamination" — the same result addressed to a community ten times larger.

Missing from an ML-rigor standpoint: no data versioning beyond the ledger — a content hash of the loaded archive would make "the run used this data" checkable the way the prereg hash makes "the run used this rule" checkable.

7 What it needs to be good (finish what is promised)

Everything here closes gaps against the project's own spec. No new ideas required.

  1. Run the ingest, paced. 64 remaining release days at a Dukascopy-respecting cadence. The single highest-value action available; every unmeasured channel is blocked on it, and the ledger already makes it a resume, not a rebuild.
  2. Raise MIN_REVISED_PERIODS_FIXTURE from 8 to 50. Real vintages are loaded; the spec requires it; it is one line plus whatever the suite then reveals.
  3. Land the BLS .xls release-schedule join so EMPLOY vintages upgrade from month precision to date. Right now the macro store proper cannot answer the intraday questions the project exists for — only the Phase 6 side-path can.
  4. A human review pass over the code. The commits say it hasn't happened. Given the project's own thesis about plausible-looking wrong output, this is not optional hygiene; it is the project applying its standard to itself.
  5. Screenshots in the README. The dashboard has, by its own admission, never been looked at. Open it, look at it, fix what's ugly, show it.

8 What it needs to be great

  1. Extend to 2015–2024 and to 3–4 instruments spanning a spread range. ~240 events per instrument, and the mid-price channel becomes a curve (cost vs spread regime) instead of a point. The cross-instrument gradient is the practitioner deliverable.
  2. The flip-decomposition estimator for revision leakage (§5). P(sign flip) from six decades of vintage data, conditional impact from the event study. This turns the "28 years needed" wall into a solvable estimation problem and would be the project's first genuinely novel methodological contribution.
  3. Replace t-tests with block-bootstrap CIs on the paired differences at full sample, given heavy tails and the mixture distribution of the revision channel.
  4. Solve the second feed. Either accept the headless-browser dependency for HistData behind an optional extra — the constraint forbids accounts, not browsers — or find another account-free tick source. H4, the cross-feed disagreement rate, is arguably the most interesting promised number still missing.
  5. Content-hash the data as the prereg is hashed. A result stamped with (rule hash, data hash) is a reproducibility claim; with only the rule hash it is half of one.
  6. The ML arm (§6): identical simple model trained per regime, validation-metric inflation reported per channel.

9 What it needs to be attention-worthy to other experts

Attention is earned by artifacts other people can use or must respond to. Three candidates, in order of effort-to-impact:

  1. Publish the ALFRED silent-vintage failure as a standalone note — blog post at minimum, a short SSRN note defensibly. "Your real-time macro data may be current data: a silent failure in keyless ALFRED access", with the byte-identical-payload evidence. The one finding where the project knows something the field demonstrably needs to know.
  2. Extract the acceptance suite into a reusable point-in-time correctness kit — a pytest package anyone can point at their own store via a small adapter (the four families plus the mutation checks). Nothing like it exists as open source; feature-store and quant-data teams alike would use it; it is 80% written.
  3. Write up the completed experiment + the flip-decomposition method as a working paper: "How much data does it take to measure backtest contamination? Channel-dependent power in event-study backtests." The finding that contamination channels differ by two orders of magnitude in measurability — and that most published event-study samples cannot resolve the revision channel they implicitly claim to handle — is a reviewable claim with teeth.

What will not earn attention: the infrastructure itself. Three-tier stores and bitemporal schemas are competent, not novel. The epistemics — prereg hashes, structural underpowered flags, provenance-typed dashboards — are the differentiated material, and they only become visible to others through the three artifacts above.

10 UI review

Reviewed from docs/ui-design.md and the src/fxpit/web/ source — ~1,800 lines of Python, ~2,400 of templates/CSS, zero external dependencies.

What is genuinely excellent

  • Provenance as a required type is the best idea in the UI and this reviewer has not seen it elsewhere: Panel raises without a provenance; a DEMO panel raises unless it names the phase replacing it; the badge is rendered by the layout macro so no template can omit it; demo cards are dashed and hatched so a screenshot pasted into a slide still announces itself. The project's data ethics extended into pixels, coherent all the way down.
  • Chart + table view from the same call, with the table required by the type system — accessibility that cannot drift from the picture, doubling as the documented relief for the light-mode contrast WARN. Most production dashboards at actual funds do not meet this bar.
  • The palette was validated by script, not by eye — all-pairs CVD ΔE checked in both modes, the one WARN documented with a structural mitigation, and a hard 3-series cap where the palette stops clearing the floor. The negative-bar incident — a crossed-quote spread rendered outside the viewBox, fixed with a proper zero baseline rather than clamped away, because that bar is the point of the panel — is the design document's best moment.
  • Prospectus-first information architecture — leading with the research document rather than the status board — is the right call for a project whose interesting claim is differences between regimes, not any single number.
  • No external requests, anywhere — no CDN, fonts, chart library, or telemetry — honors the project's defining constraint in a layer where nobody would have checked.

What holds it back

  • Nobody has ever looked at it. The design doc says so in bold: no browser was available; geometry checks substitute for the most likely mechanical failure, but typography, rhythm, and whether it actually looks good are unjudged. For a UI this is the difference between designed and specified. One Playwright pass producing screenshots — which then belong in the README — closes this; a visual regression baseline keeps it closed.
  • The hand-rolled 40-line htmx shim is a small liability wearing a big library's name. Honestly documented, but a file called htmx.min.js that is not htmx will eventually surprise someone. Rename it or vendor the real thing.
  • demo.py survives against its own rule. All seven phases are built, the design doc calls deleting this module "a project milestone, not a chore" — yet it remains because Phase 6 still imports demo.hypotheses(). Hypothesis text is static content, not synthetic data; move it and take the milestone.
  • The 3-series cap will collide with the 7-major universe the moment a coverage or flag-distribution panel wants all pairs at once. The cap is correct — the palette genuinely stops working — but the sanctioned alternative (small multiples or a sequential-scale matrix) should be designed before the need arrives.
  • Single-user, no auth, localhost — appropriate to scope, worth one explicit sentence in the docs so nobody deploys it otherwise.

UI verdict: as a dashboard, unverified visually and therefore unfinished. As a design system for honest reporting — provenance typing, enforced accessible twins, validated color, demo data that cannot masquerade — it is the strongest part of the project after the query layer, and worth extracting and reusing independently of fxpit.

Bottom line: a serious piece of work whose value is currently locked up in its least visible parts. Finish the ingest, apply human review, extract the three publishable artifacts (§9), and it graduates from "impressive portfolio project" to "thing other experts cite." Leave it as is, and it remains what it honestly says it is: a well-built instrument that has taken one good measurement.
