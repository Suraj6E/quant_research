Phase 3 — Bitemporal macro store

Ingest vintages into macro_observation, reconstruct release timestamps, and implement as_of(t) in the DuckDB layer. This is the phase that turns the red suite green.

Exit criterion: the no-clairvoyance and revision test families are green. planned

The mechanism

{{ m.card_open('Two columns, always both', 'recorded', '') }}

ref_period — the period the value describes.
known_at — the moment it became public.

A point-in-time read filters known_at <= t and keeps the latest known_at per key. You get what the world believed at t, not what turned out to be true later. Revisions fall out automatically.

That is the entire mechanism. Everything else is plumbing.

Why TIMESTAMPTZ, never DATE. An 08:30 ET release and an 08:31 ET price are different objects. A date-only column silently collapses them, and a strategy holding minutes would be entering on news it could not have heard.

A table with only ref_period is not point-in-time and cannot be made so retroactively — the information was never recorded.

The hard part

{{ m.card_open('Release timestamps have to be reconstructed', 'recorded', '') }}

RTDSM gives vintage dates, not release times. ALFRED's real-time axis is date-granularity too — it says a value became known on 2024-02-02, not at 08:30:00 ET. Neither source solves timing.

Times come from BLS/BEA schedules, which are largely stable (08:30 ET for most US releases) but have changed historically. The Phase 0 source check turned up Release_-Dates-Employment_Situation-BLS.xls on the Philadelphia Fed site, which covers a good part of this — note it is legacy .xls, needing a different reader than the .xlsx vintage files.

Unknown means unknown. Where a release time cannot be sourced, record it as explicitly unknown. Assuming 08:30 ET would manufacture precision that was never measured — which is the same error as using a revised value, wearing different clothes.
