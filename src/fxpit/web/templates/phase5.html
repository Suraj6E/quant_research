Phase 5 — Validation harness

The acceptance suite in CI against real stores, spread and tick-rate monitoring, and an independent drift anchor. The theme is that a check which cannot fail is decoration — so each one here is tested for whether it would actually fire.

Exit criterion: a green, scheduled test suite plus a reconciliation report. ✓ met CI in .github/workflows/ci.yml: unit tests on every push, full suite against real Postgres and ClickHouse containers, daily on a schedule.

The −1 h miss is real and is reported rather than hidden. With only two overlapping observations the anchor lacks the power to catch an error in that direction. That is precisely why it reports a trend instead of a verdict: a single day's difference means nothing, and what matters is whether the mean stays near zero as the sample grows.

The 5 h 45 m row is not hypothetical. Phase 4's calendar export stripped tzinfo, the driver read the naive datetime as machine-local, and on a UTC+5:45 machine every calendar hour shifted — making a detector return zero flags instead of raising. This anchor would have caught it.

Ratio to the median rather than an absolute floor, because tick rates differ by an order of magnitude between instruments and sessions. An absolute threshold would flag every Asian hour and miss a real outage in London.

CI

{{ m.card_open('Two jobs, deliberately separated', 'recorded', '') }}
fast Unit tests only, no services. Seconds on every push. This is what tells you a decoder or a DST rule broke.
stack The same suite plus integration tests against real Postgres and ClickHouse containers. A point-in-time guarantee proved against fixtures is a weaker claim than the same guarantee proved against the real stores.
Schedule Daily. The suite is not only a regression check — running it on a schedule is what catches an external source changing shape underneath the pipeline, which has already happened twice in this project.
