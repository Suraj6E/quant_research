The US springs forward on the second Sunday of March and the EU on the last; in autumn the EU falls back first. For roughly 20 trading days a year the most liquid window of the FX day is an hour longer than normal — and nothing in the code special-cases that. Sessions are defined in local wall-clock time and converted to UTC, so daylight saving falls out of the conversion.

This is the artefact hypothesis H6 predicts. Its existence is now measured; whether it is economically meaningful is still open.

A silent timezone bug, caught during this phase. The first calendar export stripped tzinfo before inserting into ClickHouse, so the driver read each naive datetime as machine-local and converted it. On a machine at UTC+5:45 every calendar hour landed at :15 past, the detector's hour join matched nothing, and rollover_window returned zero flags instead of raising. Plausible-looking wrong data, no error — which planning.md rates as the highest-likelihood risk in the project. It now has a regression test.

Why ranges, not timestamps

{{ m.card_open('TSTZRANGE with GiST exclusion constraints', 'recorded', '') }}

Windows are stored as ranges rather than (start, end) column pairs for three reasons. Containment is the query — span @> ts, index-backed, instead of a pair of inequalities. The exclusion constraint makes overlapping windows for the same session impossible rather than merely unlikely, so a DST bug emitting two overlapping London sessions fails at write time instead of double-counting at read time. And it is the modelling technique the architecture doc names as directly transferable.

The ClickHouse mirror flattens the same data to hour buckets, because ClickHouse cannot join on inequality and has no correlated subqueries — both failed on first attempt. That is lossless only because every boundary here already falls on an hour, and it is worth stating that storing a range as an enumeration is reasonable at 17,500 rows and absurd at tick scale.
